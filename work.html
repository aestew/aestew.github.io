Feature
Engineering

Most of the lift in a production ML system comes before the model sees a single batch. I build features that encode domain knowledge — population-weighted spatial aggregation, rolling temporal windows, transforms that keep features extrapolable (like the sqrt(BEV) move that fixed EV tail behavior in ClimateFEAT). Feature design is usually where the OOD performance gap gets opened.

02

Model
Selection

I pick the model that wins on the test distribution I actually care about, not the one that wins on a random holdout. That means time-aware validation, OOD test splits, and always running a boring baseline (LightGBM, usually) so I know what a fancy architecture is actually buying me. Sometimes the baseline wins. Sometimes a custom transformer with cross-stream attention wins. The point is to find out honestly.

03

RAG
Systems

I build retrieval pipelines that stay grounded in source material, not model priors. The Wattson RAG system is the current production example: 20 curated CEC and methodology documents, chunked into 438 embeddings via Voyage AI's voyage-3.5-lite, stored in ChromaDB, and composed with Claude for generation. The hard parts are never the embedding call — they're corpus curation, chunking strategy, and keeping the retrieved context relevant enough that generation doesn't drift.

04

End-to-End
Products

A model alone is not a product. I build the whole thing: ingestion pipelines, training infrastructure, batch inference, the web app, and the monitoring to know when it's drifting. Wattson is the clearest recent example — URMA/LOCA2 climate data at 2.5km resolution, through a custom PyTorch transformer, through CMIP6 inference across 12 scenario × SSP combinations, out to a Streamlit app with choropleth maps and a RAG chat interface. All of it shipped and demoed to the California Energy Commission.
